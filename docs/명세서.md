# 쇼핑몰 플랫폼 기능 요구사항 명세 (BE/FE 역할 분담용)

2026년 11월 3일 · @김도현

## 개요

일반 사용자는 상품을 조회·장바구니·주문하고, 판매자는 브랜드와 상품·재고를 관리하며 판매 통계를 보고, 서비스 관리자는 판매자 승인과 카테고리·회원을 관리하는 멀티 셀러 쇼핑몰이다. 백엔드는 Java/Spring Boot REST API, 프론트엔드는 React + TypeScript SPA로 분리한다.

> **[2026-11-10 회의로 변경]** 무신사를 참고한 패션 전용 쇼핑몰로 정했다. 판매자 승인과 카테고리 관리는 없어지고, 관리자는 브랜드 승인·상품 승인·유저 관리를 한다. 아래 "역할별 권한"·"ERD 엔티티 요약"·"ERD 보완 포인트"는 처음 안이고, 확정 내용은 [회의 결정](#회의-결정-2026-11-10)과 [DB 확정안](#db-확정안-be-1-v4--2026-11-10)을 따른다.

### 역할별 권한

| 역할 | 주요 기능 | 접근 화면 |
| --- | --- | --- |
| 비회원 | 상품 목록/상세 조회, 회원가입, 로그인 | 메인, 상품, 로그인/가입 |
| 일반 사용자 (USER) | 장바구니, 주문/구매, 주문 내역, 판매자 등록 신청 | + 장바구니, 주문, 마이페이지 |
| 판매자 (SELLER) | 브랜드 등록, 상품 등록/수정, 재고 입출고, 판매 주문 확인, 판매 통계 | + 판매자 센터 |
| 서비스 관리자 (ADMIN) | 판매자·브랜드 승인, 카테고리 관리, 회원/상품 관리, 전체 통계 | + 관리자 콘솔 |

### ERD 엔티티 요약

| 엔티티 | 역할 | 핵심 관계 |
| --- | --- | --- |
| USER | 모든 회원 계정 (로그인 주체) | SELLER 0..1, CART 0..1, ORDERS 0..N |
| SELLER | 사업자 정보 (USER가 등록) | BRAND 0..N, PRODUCT 0..N |
| BRAND | 판매자가 관리하는 브랜드 | PRODUCT 0..N (상품의 브랜드는 선택) |
| CATEGORY | 상품 분류 | PRODUCT 0..N |
| PRODUCT | 판매 상품 | INVENTORY 1:1, STOCK_HISTORY 0..N |
| INVENTORY | 상품별 현재 재고 수량 | PRODUCT 1:1 |
| STOCK_HISTORY | 재고 변동 로그 (입고/주문/취소) | PRODUCT N:1 |
| CART / CART_ITEM | 사용자당 장바구니 1개와 담긴 상품 | CART 1 : CART_ITEM 0..N |
| ORDERS / ORDER_ITEM | 주문 헤더와 주문 상품 라인 | ORDERS 1 : ORDER_ITEM 1..N |

## ERD 보완 포인트

현재 ERD로 요구 기능 대부분을 커버하지만, 역할 구분·가격 스냅샷·통계 집계를 위한 컬럼 몇 개가 더 필요하다. 구현 시작 전에 팀에서 아래 항목을 확정하자.

### 추가/확인이 필요한 컬럼

| 테이블 | 제안 컬럼 | 이유 |
| --- | --- | --- |
| USER | role (USER / SELLER / ADMIN), email(UK), password(BCrypt 해시), created_at | 서비스 관리자는 별도 테이블 없이 role로 구분. Spring Security 권한 체크의 기준 |
| SELLER | user_id(FK, UK), business_number(UK), company_name, status (PENDING / APPROVED / REJECTED) | USER:SELLER = 1:0..1 보장, 관리자 승인 흐름 |
| BRAND | seller_id(FK), name(UK), status | 브랜드 등록 승인 여부 |
| PRODUCT | seller_id(FK, NOT NULL), brand_id(FK, NULL 허용), category_id(FK), name, price, status (ON_SALE / SOLD_OUT / HIDDEN), created_at | brand_id NULL = 브랜드 독립 상품 |
| INVENTORY | product_id(PK=FK), quantity, version 또는 updated_at | 1:1 관계, 동시 주문 시 락/버전 관리 |
| STOCK_HISTORY | product_id, change_qty(+/-), type (IN / ORDER / CANCEL / ADJUST), order_item_id(NULL), created_at | 재고 변동 추적 |
| CART_ITEM | cart_id, product_id, quantity, UNIQUE(cart_id, product_id) | 같은 상품 중복 담기 방지 |
| ORDERS | user_id, status (PAID / SHIPPING / DELIVERED / CANCELED), total_price, created_at, 배송지 | 주문 상태 관리 |
| ORDER_ITEM | order_id, product_id, quantity, unit_price, (seller_id) | 주문 당시 가격 스냅샷. 판매자별 통계 집계에 필요 |
| CATEGORY | name, parent_id(NULL 허용) | 대/소분류가 필요하면 자기참조 |

### 설계 시 주의할 점

- 상품에 brand_id가 있으면 그 브랜드의 seller_id와 상품의 seller_id가 같아야 한다. DB 제약으로 걸기 어려우므로 서비스 계층에서 검증한다.
    - → **[V4 반영]** 회의에서 모든 상품이 브랜드에 속하기로 정해, 상품에 seller_id를 따로 두지 않는다. 판매자는 brands.seller_id로 정해지므로 두 값이 어긋날 수 없다. (V3까지는 복합 FK `(brand_id, seller_id)`로 강제했다.)
- 결제 테이블이 없으므로 결제는 "주문 생성 = 결제 완료"로 가정한 모의 결제로 처리할지 결정이 필요하다.
- 통계(일/주/월 판매량)는 ORDER_ITEM × ORDERS.created_at을 GROUP BY로 집계한다. 데이터가 많아지면 일별 집계 테이블(daily_sales)을 추가하는 것을 2차 과제로 둔다.
- USER는 PostgreSQL 예약어, ORDER는 MySQL/PostgreSQL 예약어이므로 실제 테이블명은 users, orders처럼 복수형으로 통일하는 편이 안전하다.
- 사용 DBMS(MySQL / PostgreSQL)를 먼저 확정해야 DDL, 날짜 함수(DATE_FORMAT vs date_trunc)를 맞출 수 있다.

## 회의 결정 (2026-11-10)

무신사를 참고한 **패션 전용** 쇼핑몰로 방향을 정했다. 이 결정이 위의 "역할별 권한", "ERD 엔티티 요약", "ERD 보완 포인트"보다 우선한다.

| 구분 | 결정 |
| --- | --- |
| 회원 | 회원제 — 가입·로그인을 빼면 모든 기능(상품 조회 포함)은 로그인해야 이용 |
| 가입 | 가입할 때 **일반회원 / 판매자** 중 선택. 판매자는 사업자 정보(사업자번호·상호·대표자명) 입력, 승인 없이 바로 활동 |
| 관리자 | users 안에 role=ADMIN 으로 두고 계정은 미리 만들어 둔다. 가입으로는 관리자가 될 수 없다 |
| 관리자 업무 | **브랜드 승인, 상품 승인, 유저 관리**(정지·해제, 탈퇴 처리). 판매자 승인·카테고리 관리는 없음 |
| 판매자 업무 | 브랜드 등록, 상품 등록, 배송 관리 |
| 브랜드 | 브랜드를 먼저 등록해 승인받아야 상품 등록 가능. 모든 상품은 브랜드에 속함 |
| 상품 등록 | 사진, 품번, 성별(남성/여성/공용), 시즌(24SS·24FW 형식), 출고 예정(주문 후 N일), 카테고리, 가격, 색상·사이즈(미리 정한 목록에서 선택) |
| 상품 승인 | 등록하면 승인 대기 → 관리자 승인 후 구매자에게 보임. **정보 수정 시 재승인, 승인 전까지 숨김.** 재고 변경과 삭제는 승인 불필요 |
| 재고 | 색상 × 사이즈 **옵션 단위**로 센다 |
| 사진 | 파일 업로드, 서버 폴더 저장. 시연은 품목별 샘플 이미지 사용 |
| 카테고리 | 패션 분류로 DB에 고정 (상의 / 아우터 / 바지 / 원피스·스커트 / 신발 / 가방 / 모자 / 액세서리 + 소분류) |
| 홈 | 카테고리별 상품, **먼저 등록한 상품이 앞** (정렬 알고리즘 없음) |
| 검색 | 상품명 · 브랜드명 · 품번 |
| 장바구니 | 체크한 상품만 합계, **체크 상태는 DB에 저장**해 다시 들어와도 유지 |
| 결제 | 실제 결제 없음. FE에서 "결제가 완료되었습니다"만 표시 (주문은 생성) → **11-19 변경: 모의 결제(아래 팀 결정 2026-11-19)** |
| 좋아요 | 내가 좋아요 누른 상품 목록 |
| 주문·배송 | 장바구니에서 한 번에 주문, **배송 상태는 판매자별.** 주문완료 → 배송준비 → 배송중 → 배송완료 → 구매확정 |
| 구매확정 | 구매자가 배송완료 후 누름 → 판매자 화면에도 확정, 이후 수정 불가 |
| 취소 | 유지. 판매자별로, 주문완료 상태에서만 → **11-20 추가: 판매자도 배송 전까지 취소 가능(사유 필수)** |
| 유지하는 기존 기능 | 재고 입고·변동 이력, 판매 통계(일/주/월), 거절 사유 |

## 팀 결정 (2026-11-17) — 계정 관리 추가

"진행 중인 주문" = 배송 묶음(shipments)이 **주문완료·배송준비·배송중**. 배송완료·구매확정·취소는 끝난 주문으로 본다. 구매자는 내가 한 주문, 판매자는 내 상품에 들어온 주문.

| 구분 | 결정 |
| --- | --- |
| 관리자의 정지·탈퇴 | 진행 중인 주문이 있는 구매자·판매자는 **정지·탈퇴시킬 수 없다** → 409 `HAS_IN_PROGRESS_ORDERS`, FE는 message를 팝업으로. 정지 해제는 항상 가능. 관리자 계정은 원래대로 변경 불가 |
| 정지된 판매자 | 정지 중에는 그 판매자의 상품을 **주문할 수 없다**(`PRODUCT_NOT_PURCHASABLE`). 상품 목록에는 그대로 보이고, 해제하면 다시 주문 가능 |
| 본인 탈퇴 | 탈퇴 버튼 → 확인 API로 팝업 문구를 받아 표시("진행 중인 주문이 N건 존재합니다. 정말 탈퇴하시겠습니까?") → **비밀번호 다시 입력** 후 탈퇴 |
| 본인 탈퇴 — 구매자 | 진행 중인 주문이 있어도 탈퇴 가능. 주문은 그대로 남고 배송은 판매자가 계속 진행 |
| 본인 탈퇴 — 판매자 | 진행 중인 주문이 있으면 탈퇴 불가 (탈퇴하면 배송할 사람이 없음). 탈퇴하면 상품 모두 판매 종료 |
| 마이페이지 | 계정 정보(이메일=계정명, 이름, 전화번호, 회원 종류, 가입일, 판매자면 상호·대표자명·사업자번호) 보기. 모든 회원이 이름·전화번호·비밀번호 수정, 판매자는 상호·대표자명도 수정 (사업자번호는 고정) |
| 비밀번호 변경 | 현재 비밀번호 확인 후 변경, **바꾸면 로그아웃** → 새 비밀번호로 다시 로그인 |
| 동시 로그인 | 같은 계정으로 다른 곳에서 로그인하면 **먼저 로그인한 쪽이 끊긴다**. 끊긴 쪽은 다음 요청에서 401 `LOGGED_IN_ELSEWHERE` → FE 팝업 후 로그인 화면 |
| 우편번호 | 주문서 입력 칸에 "숫자 5자리" 안내 문구 (FE). 서버 검증(숫자 5자리)은 이미 있음 |

## 팀 결정 (2026-11-19) — 모의 결제

"결제 버튼만 누르면 완료"인 시나리오가 어색해서, 실제 PG 없이 서버가 결제를 승인하고 기록을 남기도록 바꿨다 (README 9장).

| 구분 | 결정 |
| --- | --- |
| 결제 단계 | 주문과 결제를 한 번에 (`POST /api/orders` 한 트랜잭션). 결제가 거절되면 주문·재고·장바구니 모두 그대로 |
| 결제수단 | 카드 · 계좌이체 · 간편결제. 계좌이체·간편결제는 수단만 고름 |
| 카드 정보 | 카드번호 16자리 입력, **끝 4자리만 저장** |
| 금액 | 클라이언트는 금액을 보내지 않음. 서버가 계산한 주문 총액으로 승인 |
| 실패 시연 | 카드번호가 0000으로 끝나면 카드사 거절, 100만 원 초과면 모든 수단에서 한도 초과 → 402 `PAYMENT_DECLINED` |
| 취소 | 판매자별 배송 묶음 취소 = 그 묶음 금액만큼 부분 환불 기록 |
| 예전 주문 | 결제 기능 전 주문은 결제 없음. 시연 주문에만 결제·환불 기록을 채움 |
| 프론트 | 결제 정보 필수 → 프론트가 맞춘 뒤 main(서버)에 함께 반영 |

프론트 점검에서 브라우저 저장소로 흉내 낸 기능 5가지를 서버 기능으로 옮겼다 (README 10장).

| 브랜드별 매출 | 서버 집계 (취소 제외, 주문일 기준) |
| 목록 옵션 | 판매자·관리자 상품 목록에 옵션 포함, 프론트는 페이지를 이어서 조회 |

### V3 → V4 주요 변경

| 변경 | 이유 |
| --- | --- |
| `sellers.status / reject_reason / approved_at` 삭제 | 판매자 승인 단계 없음 |
| `products.seller_id` 삭제, `brand_id` NOT NULL | 모든 상품이 브랜드 소속 → 판매자는 brands.seller_id로 정해진다. 남겨 두면 이행 종속(3NF 위반). 위 "설계 시 주의할 점"의 브랜드-판매자 일치 문제도 구조적으로 사라졌다 |
| `inventory`(상품 1:1) 삭제, `product_options` 추가 | 재고를 옵션 단위로. 상품 정보와 재고가 다른 행이라 주문이 상품 수정을 막지 않는다 |
| `colors`, `sizes` 추가 | 미리 정한 목록 → 표기 차이 없이 필터·통계 가능, 목록 밖 값은 FK가 거부 |
| `orders.status / canceled_at` 삭제, `shipments` 추가 | 배송 상태·취소·구매확정이 판매자별 |
| `order_items`: order_id·seller_id·product_id → shipment_id·option_id | 주문·판매자는 배송 묶음으로, 상품은 옵션으로 도출 (중복 저장 안 함) |
| `cart_items`: product_id → option_id, `selected` 추가 | 색상·사이즈까지 정해 담기, 체크 상태 유지 |
| `likes` 추가 | 좋아요 |
| `users.status`에 WITHDRAWN, `withdrawn_at` | 유저 삭제 = 탈퇴 처리. 행을 지우면 주문 기록이 깨지므로 개인정보만 지운다 |
| `brands.reject_reason`, `products.reject_reason` | 거절 사유 |
| 카테고리 교체 + `size_group` | 패션 분류 고정, 카테고리마다 사이즈 체계 |

### DB 제약으로 강제하는 규칙

| 규칙 | 제약 |
| --- | --- |
| 이메일·사업자번호·브랜드명 중복 금지, 회원당 판매자 1개·장바구니 1개 | UNIQUE |
| 품번은 브랜드 안에서 유일 / 같은 상품의 같은 색상·사이즈 옵션은 하나 | UNIQUE |
| 장바구니의 같은 옵션 / 한 주문의 같은 판매자 / 배송 묶음의 같은 옵션은 하나 | UNIQUE |
| 같은 상품에 좋아요 한 번 | 복합 PK |
| 모든 상품은 브랜드 소속, 색상·사이즈는 목록 안에서만 | NOT NULL + FK |
| 시즌 24SS/24FW 형식, 성별, 출고 0~30일, 사업자번호 숫자 10자리, 상태값 | CHECK |
| 재고·가격·수량 음수 불가 (동시 주문의 최후 방어선) | CHECK |
| 재고 이력 부호, ORDER·CANCEL은 주문 라인 필수 | CHECK |
| 탈퇴 ⇔ 탈퇴 시각, 구매확정 ⇔ 확정 시각, 취소 ⇔ 취소 시각 | CHECK |

DB로 표현할 수 없는 규칙(승인된 브랜드에만 등록, 옵션 사이즈 = 카테고리 사이즈 체계, 배송 상태 순서, 취소는 주문완료에서만 등)은 서비스에서 검증한다.

## 백엔드 요구사항 (Spring Boot)

백엔드는 6개 도메인(Auth, Seller/Brand, Product/Category, Inventory, Cart/Order, Stats) 단위로 패키지를 나누고, 도메인별로 담당자를 배정한다. 권한은 Spring Security + JWT로 URL 프리픽스(`/api/seller/**`, `/api/admin/**`) 단위로 막는다.

### 공통 기반

- 프로젝트 세팅: Spring Boot 3.x, Spring Data JPA, Spring Security, Validation, Lombok, DB 드라이버
- 인증: 로그인 시 JWT(Access Token) 발급, 요청마다 필터에서 검증, role을 GrantedAuthority로 매핑
- 공통 응답 포맷 / 전역 예외 처리(@RestControllerAdvice) / 페이징 응답 DTO
- CORS 설정 (React 개발 서버 localhost:5173 등 허용)
- API 문서: Swagger(springdoc-openapi)로 FE와 계약 공유

### 핵심 비즈니스 로직 (DB 응용 평가 포인트)

> **[V4 반영]** 재고는 `inventory`가 아니라 `product_options.stock_quantity`(색상 × 사이즈 옵션 단위)에 있다. 주문은 `orders` 1건 아래 판매자별 `shipments`를 만들고, 주문 상품 줄(`order_items`)은 shipment에 속한다. 취소는 shipment 단위로 ORDERED 상태에서만 한다. 아래 SQL 예시의 `inventory`는 `product_options`로 읽으면 된다.

1. 주문 생성 트랜잭션 (@Transactional): 재고 확인 → INVENTORY 차감 → ORDERS / ORDER_ITEM 저장(unit_price 스냅샷) → STOCK_HISTORY(type=ORDER) 기록 → 주문한 CART_ITEM 삭제. 하나라도 실패하면 전체 롤백.
2. 재고 동시성: 동시에 같은 상품을 주문해도 음수 재고가 되지 않게 한다. 방법은 셋 중 하나를 택한다.
    - 비관적 락: SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE))
    - 낙관적 락: INVENTORY.version + @Version, 충돌 시 재시도
    - 조건부 UPDATE: UPDATE inventory SET quantity = quantity - ? WHERE product_id = ? AND quantity >= ? (영향 행 0이면 재고 부족)
3. 주문 취소: 상태 검증(배송 전만 가능) → 재고 복원 → STOCK_HISTORY(type=CANCEL).
4. 소유권 검증: 판매자는 본인 상품·브랜드만 수정, 상품 등록 시 brandId가 본인 브랜드인지 확인.
5. 통계 쿼리: 판매량 = SUM(order_item.quantity), 매출 = SUM(quantity × unit_price), 취소 주문 제외, 기간 단위로 GROUP BY. JPQL이 어려우면 네이티브 쿼리나 QueryDSL 사용.
6. 조회 성능: 상품 목록 N+1 방지(fetch join 또는 @EntityGraph), product(category_id), order_item(product_id), orders(created_at) 인덱스.

### 테스트 / 데이터

- 초기 데이터: 관리자 계정 1개, 카테고리, 샘플 판매자·상품·주문 (통계 화면 시연용으로 여러 날짜에 걸친 주문 포함)

## 프론트엔드 요구사항 (React + TS)

프론트엔드는 사용자 쇼핑 화면, 판매자 센터, 관리자 콘솔 3개 영역으로 나누고, 로그인 상태의 role에 따라 라우트를 보호한다. 백엔드 API 1개당 FE 화면/훅 1개가 대응하도록 Swagger 기준으로 작업한다.

### 협업 규칙

- 저장소: backend / frontend 분리 레포 또는 모노레포 중 택1
- 브랜치: main(배포) ← develop ← feature/{도메인}-{기능} (예: feature/order-create), PR 1명 이상 리뷰 후 머지
- 커밋: feat / fix / refactor / docs / test 접두어
- 네이밍: DB는 snake_case, Java·TS는 camelCase, JSON 필드는 camelCase

### 시작 전 결정할 것

- 팀 인원과 BE/FE 담당자 확정
- DBMS 선택 (MySQL / PostgreSQL) → BE-1 제안: MySQL 8.0으로 구현됨
- 결제 방식 (모의 결제로 처리할지) → **확정(11-10)**: 실제 결제 없음, FE에서 완료 메시지만
- 카테고리 계층 사용 여부 (parent_id) → **확정(11-10)**: 패션 분류 2단계, DB 고정
- 주문 상태 종류 확정 (PAID / SHIPPING / DELIVERED / CANCELED) → **확정(11-10)**: 판매자별 배송 상태 ORDERED / PREPARING / SHIPPING / DELIVERED / CONFIRMED / CANCELED
- 동시성 처리 방식 선택 (비관적 락 / 낙관적 락 / 조건부 UPDATE)
- 배포 여부와 환경 (로컬 시연 / 클라우드) → BE-1: docker-compose(MySQL + 앱)로 로컬 시연 환경 준비됨
