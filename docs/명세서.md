# 쇼핑몰 플랫폼 기능 요구사항 명세 (BE/FE 역할 분담용)

2026년 11월 3일 · @김도현

## 개요

일반 사용자는 상품을 조회·장바구니·주문하고, 판매자는 브랜드와 상품·재고를 관리하며 판매 통계를 보고, 서비스 관리자는 판매자 승인과 카테고리·회원을 관리하는 멀티 셀러 쇼핑몰이다. 백엔드는 Java/Spring Boot REST API, 프론트엔드는 React + TypeScript SPA로 분리한다.

### 역할별 권한

| 역할 | 주요 기능 | 접근 화면 |
| --- | --- | --- |
| 비회원 | 상품 목록/상세 조회, 회원가입, 로그인 | 메인, 상품, 로그인/가입 |
| 일반 사용자 (USER) | 장바구니, 주문/구매, 주문 내역, 판매자 등록 신청 | + 장바구니, 주문, 마이페이지 |
| 판매자 (SELLER) | 브랜드 등록, 상품 등록/수정, 재고 입출고, 판매 주문 확인, 판매 통계 | + 판매자 센터 |
| 서비스 관리자 (ADMIN) | 판매자·브랜드 승인, 카테고리 관리, 회원/상품 관리, 전체 통계 | + 관리자 콘솔 |

### ERD 엔티티 요약

| 엔티티 | 역할 | 핵심 관계 |
| --- | --- | --- |
| USER | 모든 회원 계정 (로그인 주체) | SELLER 0..1, CART 0..1, ORDERS 0..N |
| SELLER | 사업자 정보 (USER가 등록) | BRAND 0..N, PRODUCT 0..N |
| BRAND | 판매자가 관리하는 브랜드 | PRODUCT 0..N (상품의 브랜드는 선택) |
| CATEGORY | 상품 분류 | PRODUCT 0..N |
| PRODUCT | 판매 상품 | INVENTORY 1:1, STOCK_HISTORY 0..N |
| INVENTORY | 상품별 현재 재고 수량 | PRODUCT 1:1 |
| STOCK_HISTORY | 재고 변동 로그 (입고/주문/취소) | PRODUCT N:1 |
| CART / CART_ITEM | 사용자당 장바구니 1개와 담긴 상품 | CART 1 : CART_ITEM 0..N |
| ORDERS / ORDER_ITEM | 주문 헤더와 주문 상품 라인 | ORDERS 1 : ORDER_ITEM 1..N |

## ERD 보완 포인트

현재 ERD로 요구 기능 대부분을 커버하지만, 역할 구분·가격 스냅샷·통계 집계를 위한 컬럼 몇 개가 더 필요하다. 구현 시작 전에 팀에서 아래 항목을 확정하자.

### 추가/확인이 필요한 컬럼

| 테이블 | 제안 컬럼 | 이유 |
| --- | --- | --- |
| USER | role (USER / SELLER / ADMIN), email(UK), password(BCrypt 해시), created_at | 서비스 관리자는 별도 테이블 없이 role로 구분. Spring Security 권한 체크의 기준 |
| SELLER | user_id(FK, UK), business_number(UK), company_name, status (PENDING / APPROVED / REJECTED) | USER:SELLER = 1:0..1 보장, 관리자 승인 흐름 |
| BRAND | seller_id(FK), name(UK), status | 브랜드 등록 승인 여부 |
| PRODUCT | seller_id(FK, NOT NULL), brand_id(FK, NULL 허용), category_id(FK), name, price, status (ON_SALE / SOLD_OUT / HIDDEN), created_at | brand_id NULL = 브랜드 독립 상품 |
| INVENTORY | product_id(PK=FK), quantity, version 또는 updated_at | 1:1 관계, 동시 주문 시 락/버전 관리 |
| STOCK_HISTORY | product_id, change_qty(+/-), type (IN / ORDER / CANCEL / ADJUST), order_item_id(NULL), created_at | 재고 변동 추적 |
| CART_ITEM | cart_id, product_id, quantity, UNIQUE(cart_id, product_id) | 같은 상품 중복 담기 방지 |
| ORDERS | user_id, status (PAID / SHIPPING / DELIVERED / CANCELED), total_price, created_at, 배송지 | 주문 상태 관리 |
| ORDER_ITEM | order_id, product_id, quantity, unit_price, (seller_id) | 주문 당시 가격 스냅샷. 판매자별 통계 집계에 필요 |
| CATEGORY | name, parent_id(NULL 허용) | 대/소분류가 필요하면 자기참조 |

### 설계 시 주의할 점

- 상품에 brand_id가 있으면 그 브랜드의 seller_id와 상품의 seller_id가 같아야 한다. DB 제약으로 걸기 어려우므로 서비스 계층에서 검증한다.
    - → **[BE-1 반영]** 복합 FK `products(brand_id, seller_id) → brands(id, seller_id)`로 DB에서 강제한다. 서비스 계층 검증은 친절한 에러 메시지용으로 함께 둔다. 아래 "DB 확정안" 참고.
- 결제 테이블이 없으므로 결제는 "주문 생성 = 결제 완료"로 가정한 모의 결제로 처리할지 결정이 필요하다.
- 통계(일/주/월 판매량)는 ORDER_ITEM × ORDERS.created_at을 GROUP BY로 집계한다. 데이터가 많아지면 일별 집계 테이블(daily_sales)을 추가하는 것을 2차 과제로 둔다.
- USER는 PostgreSQL 예약어, ORDER는 MySQL/PostgreSQL 예약어이므로 실제 테이블명은 users, orders처럼 복수형으로 통일하는 편이 안전하다.
- 사용 DBMS(MySQL / PostgreSQL)를 먼저 확정해야 DDL, 날짜 함수(DATE_FORMAT vs date_trunc)를 맞출 수 있다.

### DB 제약으로 강제하는 규칙

| 규칙 | 제약 |
| --- | --- |
| 이메일·사업자번호·브랜드명 중복 금지, 회원당 판매자 1개, 회원당 장바구니 1개 | UNIQUE |
| 장바구니에 같은 상품 중복 금지 | UNIQUE(cart_id, product_id) |
| 같은 부모 아래 카테고리 이름 중복 금지 | UNIQUE(parent_id, name) |
| 상품의 브랜드는 같은 판매자 소유 | 복합 FK (brand_id, seller_id) → brands(id, seller_id) |
| 재고·가격·수량은 음수 불가 | CHECK |
| 사업자번호는 숫자 10자리 | CHECK (REGEXP) |
| 재고 이력 유형별 부호 (IN·CANCEL은 +, ORDER는 −), ORDER·CANCEL은 주문 라인 참조 필수 | CHECK |
| 취소 상태 ⇔ canceled_at 존재 | CHECK |
| 상태값은 정해진 값만 | VARCHAR + CHECK (ENUM 타입 대신) |

### 인덱스 (V3에서 변경)

처음 설계한 `(category_id, status, created_at)`, `(status, price)`는 상품 5만 건 EXPLAIN에서 풀스캔 + filesort(약 180ms)가 나왔다. status는 공개 상품이 95%라 거의 걸러내지 못하고, `status IN (...)` 범위 조건 때문에 뒤의 정렬 컬럼을 쓸 수 없었다. 그래서 다음처럼 바꿨다. 지금은 20건 안팎만 읽고 0.2ms 안팎으로 끝난다. 측정 결과는 `README.md` 5장(인덱스와 실행 계획)에 있다.

| 인덱스 | 쓰는 쿼리 |
| --- | --- |
| `products(category_id, created_at)` | 소분류 최신순 |
| `products(created_at)` | 전체·대분류 최신순 (메인 기본) |
| `products(price)` | 전체 가격순 (가격이 같으면 id를 같은 방향으로 정렬) |
| `products(seller_id, created_at)` | 판매자 내 상품 목록 |
| `orders(user_id, created_at)`, `orders(created_at, status)`, `order_items(product_id)`, `order_items(seller_id, order_id)`, `stock_history(product_id, created_at)` | BE-2 주문·통계·재고 이력 (BE-2 쿼리 확정 후 EXPLAIN으로 재확인) |

## 백엔드 요구사항 (Spring Boot)

백엔드는 6개 도메인(Auth, Seller/Brand, Product/Category, Inventory, Cart/Order, Stats) 단위로 패키지를 나누고, 도메인별로 담당자를 배정한다. 권한은 Spring Security + JWT로 URL 프리픽스(`/api/seller/**`, `/api/admin/**`) 단위로 막는다.

### 공통 기반

- 프로젝트 세팅: Spring Boot 3.x, Spring Data JPA, Spring Security, Validation, Lombok, DB 드라이버
- 인증: 로그인 시 JWT(Access Token) 발급, 요청마다 필터에서 검증, role을 GrantedAuthority로 매핑
- 공통 응답 포맷 / 전역 예외 처리(@RestControllerAdvice) / 페이징 응답 DTO
- CORS 설정 (React 개발 서버 localhost:5173 등 허용)
- API 문서: Swagger(springdoc-openapi)로 FE와 계약 공유

### 핵심 비즈니스 로직 (DB 응용 평가 포인트)

1. 주문 생성 트랜잭션 (@Transactional): 재고 확인 → INVENTORY 차감 → ORDERS / ORDER_ITEM 저장(unit_price 스냅샷) → STOCK_HISTORY(type=ORDER) 기록 → 주문한 CART_ITEM 삭제. 하나라도 실패하면 전체 롤백.
2. 재고 동시성: 동시에 같은 상품을 주문해도 음수 재고가 되지 않게 한다. 방법은 셋 중 하나를 택한다.
    - 비관적 락: SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE))
    - 낙관적 락: INVENTORY.version + @Version, 충돌 시 재시도
    - 조건부 UPDATE: UPDATE inventory SET quantity = quantity - ? WHERE product_id = ? AND quantity >= ? (영향 행 0이면 재고 부족)
3. 주문 취소: 상태 검증(배송 전만 가능) → 재고 복원 → STOCK_HISTORY(type=CANCEL).
4. 소유권 검증: 판매자는 본인 상품·브랜드만 수정, 상품 등록 시 brandId가 본인 브랜드인지 확인.
5. 통계 쿼리: 판매량 = SUM(order_item.quantity), 매출 = SUM(quantity × unit_price), 취소 주문 제외, 기간 단위로 GROUP BY. JPQL이 어려우면 네이티브 쿼리나 QueryDSL 사용.
6. 조회 성능: 상품 목록 N+1 방지(fetch join 또는 @EntityGraph), product(category_id), order_item(product_id), orders(created_at) 인덱스.

### 테스트 / 데이터

- 초기 데이터: 관리자 계정 1개, 카테고리, 샘플 판매자·상품·주문 (통계 화면 시연용으로 여러 날짜에 걸친 주문 포함)
- 동시 주문 테스트: ExecutorService로 재고 10개 상품에 동시 주문 20건 → 성공 10건, 재고 0 확인

## 프론트엔드 요구사항 (React + TS)

프론트엔드는 사용자 쇼핑 화면, 판매자 센터, 관리자 콘솔 3개 영역으로 나누고, 로그인 상태의 role에 따라 라우트를 보호한다. 백엔드 API 1개당 FE 화면/훅 1개가 대응하도록 Swagger 기준으로 작업한다.

### 공통 기반

- 세팅: Vite + React + TypeScript, React Router, 서버 상태는 TanStack Query(React Query), 전역 상태(로그인 유저)는 Zustand 또는 Context
- API 클라이언트: axios 인스턴스 + 요청 인터셉터로 JWT 헤더 첨부, 401 응답 시 로그아웃 처리
- 타입: 백엔드 DTO와 맞춘 TypeScript 타입 정의 (Swagger에서 openapi-typescript로 자동 생성 가능)
- 라우트 가드: ProtectedRoute(role) 컴포넌트로 USER / SELLER / ADMIN 페이지 접근 제어
- 공통 UI: 헤더(역할별 메뉴), 페이지네이션, 로딩/에러 표시, 토스트 알림, 폼 검증(react-hook-form)
- 차트: 판매 통계용 Recharts 또는 Chart.js

### 화면 구현 시 주의할 점

- 장바구니·주문 후에는 React Query 캐시 무효화(invalidateQueries)로 재고·장바구니 수를 갱신한다.
- 판매자 승인 직후 role이 바뀌므로 /api/users/me를 다시 불러와 메뉴를 갱신한다 (또는 재로그인 안내).
- 비회원이 장바구니 담기를 누르면 로그인 페이지로 보내고, 로그인 후 원래 페이지로 돌아온다.
- 금액은 백엔드 계산값을 표시만 하고, 최종 금액 검증은 백엔드에서 한다.

## 역할 분담 제안

4인 팀(BE 2 · FE 2) 기준으로, 백엔드는 "계정·판매자·상품"과 "주문·재고·통계"로, 프론트엔드는 "쇼핑 화면"과 "판매자·관리자 화면"으로 나누면 의존성이 가장 적다. 팀 인원이 다르면 아래 담당 단위를 합치거나 쪼개서 쓰면 된다.

| 담당 | 범위 | 주요 산출물 |
| --- | --- | --- |
| BE-1 | 공통 기반, Auth/JWT, Seller·Brand, Category, Product CRUD, Admin 승인 API | 프로젝트 골격, Security 설정, 공통 응답/예외, Swagger, DB 스키마(DDL)·초기 데이터, 배포 |
| BE-2 | Inventory, Cart, Order, Stats | 주문 트랜잭션, 재고 동시성 처리 + 테스트, 통계 집계 쿼리 |
| FE-1
임정빈 | 공통 기반, 로그인/가입, 상품 목록·상세, 장바구니, 주문/주문내역, 판매자 신청 | 라우터·라우트 가드, axios/React Query 세팅, 공통 레이아웃 |

| 단계 | 범위 | 완료 기준 |

## 공통 규약

BE·FE가 처음에 응답 포맷과 에러 코드만 맞춰 두면 연동 단계의 수정이 크게 줄어든다.

### API 응답 포맷

```json
{ "success": true, "data": { }, "error": null }
{ "success": false, "data": null, "error": { "code": "OUT_OF_STOCK", "message": "재고가 부족합니다." } }
```

- 목록 응답의 data: { content: [], page, size, totalElements, totalPages }
- 날짜: ISO-8601 문자열 (2026-11-03T12:00:00), 금액: 정수(원)

### 에러 코드 (예시)

| HTTP | code | 상황 |
| --- | --- | --- |
| 400 | INVALID_INPUT | 입력값 검증 실패 |
| 401 | UNAUTHORIZED | 토큰 없음/만료 |
| 403 | FORBIDDEN | 역할 권한 없음, 타인 상품 수정 시도 |
| 404 | NOT_FOUND | 상품·주문 등 없음 |
| 409 | DUPLICATE_EMAIL / OUT_OF_STOCK / INVALID_ORDER_STATUS | 중복 가입, 재고 부족, 취소 불가 상태 |

**[BE-1 추가]** 구현하면서 추가한 코드. 전체 목록은 `ErrorCode.java`와 Swagger에 있다.

| HTTP | code | 상황 |
| --- | --- | --- |
| 400 | CATEGORY_NOT_LEAF / CATEGORY_DEPTH_EXCEEDED | 대분류에 상품 등록, 3단계 카테고리 생성 |
| 401 | INVALID_CREDENTIALS | 이메일·비밀번호 불일치 |
| 403 | ACCOUNT_SUSPENDED / SELLER_NOT_APPROVED / BRAND_NOT_OWNED / PRODUCT_NOT_OWNED / CANNOT_MODIFY_ADMIN | 정지 회원, 승인 전 판매자, 타인 브랜드·상품, 관리자 계정 변경 시도 |

| 409 | BRAND_NOT_APPROVED / CATEGORY_IN_USE / PRODUCT_BLOCKED / INVALID_STATUS_TRANSITION / DATA_CONFLICT | 승인 전 브랜드 지정, 사용 중 카테고리 삭제, 차단 상품 상태 변경, 이미 처리된 승인, 기타 DB 제약 위반 |

### 협업 규칙

- 저장소: backend / frontend 분리 레포 또는 모노레포 중 택1
- 브랜치: main(배포) ← develop ← feature/{도메인}-{기능} (예: feature/order-create), PR 1명 이상 리뷰 후 머지
- 커밋: feat / fix / refactor / docs / test 접두어
- 네이밍: DB는 snake_case, Java·TS는 camelCase, JSON 필드는 camelCase
